# 第二次作业 · 小组开工说明

## 项目从哪里来，当前做到哪一步

第一阶段完成了《项目立项与需求文档》3.0 版，确定了目标用户、功能与质量需求、用例、验收条件和四人协作。赛题工程已有球检测、轨迹、球桌几何、触台判断和评估结果。可以继承的是识别组件，以及从 0 开始的原片帧号、原图像素坐标和结果文件等约定。

原赛题的完整分析流程面向云端双 RTX 4090。课程项目面向普通 Windows 电脑，目标是让复核人员导入本地录像，在 CPU 上分析或加载已有结果，核查原片与俯视落点，再保存或导出。当前仓库的 V0 用合成样片演示加载已有结果与人工复核。研发环境曾用 v75（25 fps）和 Rocket50（50 fps）核对跳帧与复核，仓库内置的 25 fps 和 50 fps 合成样片用于复现操作。长视频性能、真实视频定位精度和异机可用性分别验收。

## 第二次作业交什么

全组提交一份系统设计文档，依次写清以下内容。

|内容|写到什么程度|
|---|---|
|第一阶段承接|列出已有需求文档、可复用的代码和结果、这次扩展到本地设备和高帧率的范围。|
|体系结构风格及理由|用一张图说明工作台、后台分析和存储如何分层。可评估本地模块化单体，解释离线部署、CPU 负载和界面响应的取舍。|
|模块划分和接口约定|说明视频解码、轨迹、球桌、触台、复核和存储各自的职责、输入、输出、缺失值与报错。至少用同一条事件走完各模块。|
|至少 3 条架构决策记录（ADR）|每条写问题、备选方案、决定、理由、代价和验收方法。可选主题为本地架构、后台分析、原片帧与时间、预测和人工意见分开保存。|
|关键构件详细设计|给出原帧定位、轨迹与球桌投影、触台判断、人工复核或结果存储的流程图或状态图，写清异常处理及可验收行为。|

## 接口先用一条落点讲清楚

V0 已有文件接口。`run.json` 核对视频身份、尺寸和帧数，`tracks.json` 传球点，`landings.json` 传触台候选。每个候选至少有 `frame_id`、`timestamp_s`、`x` 和 `y`。样片的同一时刻在 50 fps 对应 `f90`，在 25 fps 对应 `f45`。帧号从 0 开始，坐标以原图左上为原点，向右和向下为正。

V1 需要约定原视频帧号与时间戳怎样传递，时间戳无效或者视频身份对不上时怎样反馈，四角缺失时怎样提示，重新分析后怎样关联原人工记录。CPU 初筛可沿用约 40 ms 的取样网格，碰到候选时回到附近真实源帧再定位。原视频的帧率用于读取和验收，25 Hz 是候选分析的内部设置。

## 四个人接下来怎么做

|成员|任务|在共同样片上验证|
|---|---|---|
|A 工作台与集成|维护课程基线，画总体模块图，设计视频导入、后台任务状态、窗口联动、保存和导出。|请一位组员照 README 独立启动，再演示点击同一事件如何同步三窗。|
|B 数据与验收|整理样片、预期帧号和用例表，设计真实高帧率、换机器、无事件及损坏输入的验收。|对照两段样片检查同一时间对应的源帧，记录实际结果、设备和版本。|
|C 视频与观测|设计视频时间戳、原图轨迹、球桌四角与 A/B 方向的接口，给 D 一份观测样例。|核对 `f90` 和 `f45`，检查逐帧与交换 A/B 后的投影。|
|D 触台与复核|设计候选事件、确认、驳回、疑难、补记和重跑后的记录关系。|点事件跳帧，保存一条疑难或补记，重开核对。|

第一次组会由 A 演示样片，B、C、D 一起定帧号、时间、坐标和数据异常的处理。此后每人交自己的构件设计、一个接口样例、一条 ADR 草稿和一个验收用例。A 汇总，B 走查，C 与 D 互查接口。提交前逐项对照作业清单，从同一条落点讲通原片、俯视位置和人工记录。
